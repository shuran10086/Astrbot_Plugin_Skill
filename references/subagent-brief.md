# 子代理派单与验收模板

> 触发条件：要用子代理做 AstrBot 插件相关调研、实现、测试、审查时读本文件。
> 前提：子代理与你同一质量与流程标准；派单不自包含就等于没派。

## 1. 派单前先想清三件事

1. **能不能不派**：需要连续上下文判断的核心设计（架构、配置 schema 取舍、事件接线）自己写，拆出去只会返工。
2. **写入范围是否冲突**：两个子代理不许同时写同一文件或同一目录。按目录/文件切开，写进 brief。
3. **验收标准是什么**：派单里没有验收标准，就别派。

## 2. Brief 模板（复制后逐项填满，不许留空）

```markdown
## 项目背景
- 项目：<插件名 / 仓库路径>；AstrBot 版本：>=x.y.z；Python：x.y
- 现状：<已有什么、缺什么、相关文件路径>
- 上游约束：<仓库规范、既有风格、必须复用的模块>

## 本次任务
- 目标：<一句话，可验收>
- 具体交付：<要产出哪些文件 / 哪份文档 / 哪种报告>
- 明确不做：<排除项，防止越界>

## 权威依据（先读再动手）
- <官方文档链接与需要看的小节>
- <仓库内相关源码路径>
- <参考的开源实现链接，说明只学结构不搬运>

## 写入范围（其余文件只读）
- 允许修改：<文件/目录清单>
- 只读：<其余>
- 冲突声明：<同一时间没有其他人写这些文件>

## 质量标准
- 类型标注齐全、分层清晰、低耦合；网络用 aiohttp/httpx；持久化只写 data/；异常有兜底
- 提交前 ruff format + ruff check 通过
- 不臆造 API，字段与签名以官方文档/源码为准

## 验收方式
- <可复制执行的命令 / 测试用例 / 检查清单>
- 通过判据：<逐条列出，可打勾>

## 回报格式（缺项视为未完成）
1. 做了什么（按文件列）
2. 关键决策与理由（含放弃的方案）
3. 验证结果（命令 + 实际输出摘要，不许只说"通过"）
4. 未解决项 / 风险 / 需要我决策的点
5. 参考过的文档与外部项目链接
```

## 3. 常见分工（按需选用，不要全部同时开）

| 分工 | 适合派 | 交付物 | 注意 |
|---|---|---|---|
| 文档调研员 | 阶段 0 | 调研摘要（链接 + 可取用点 + 版本差异坑） | 明确要求区分"官方文档"与"社区博客" |
| 同类实现分析 | 阶段 0 | 2-3 个开源插件的结构对比与取舍建议 | 只学结构，不抄代码；记录许可证 |
| 模块实现 | 阶段 6 | 指定目录下的实现 + 自测 | 写入范围严格切开 |
| 测试员 | 阶段 6 | 用例清单 + 执行结果 + 缺陷单 | 必须给可复现步骤 |
| 代码审查员 | 阶段 6 | 问题清单（严重度、文件行号、修复建议） | 不直接改代码，除非 brief 授权 |
| 文档审查员 | 阶段 4 | 自审清单逐条结论 | 只挑错，不重写 |

## 4. 验收（子代理回报后由你做）

- [ ] 交付物与 brief 的"具体交付"逐条对上
- [ ] 写入范围没有越界（`git status` / 文件时间戳核对）
- [ ] 验证结果可复现：自己跑一遍命令，结果一致
- [ ] 质量项抽查：类型标注、异常兜底、网络库、持久化路径、ruff
- [ ] 关键决策合理，没有静默改需求
- [ ] 有未解决项就明确记录，不当成已完成

任何一项不过 → 带具体问题回派一次；两次不过就收回自己做，并记录原因。

## 5. 并行与冲突规则

- 并行上限按任务独立性定，别为了并行硬拆；串行成本更低的就串行。
- 所有子代理共享同一工作区，编辑立即互相可见：写同一文件必须串行。
- 需要串行依赖时显式说明"等 X 完成后再开始"，不要靠子代理互相猜。
- 汇总时以你自己的复验结果为准，不以子代理的自述为准。
